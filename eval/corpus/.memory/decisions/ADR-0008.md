# ADR-0008: Hybrid Retrieval

## Context

No single retrieval method reliably handles all memory questions. Semantic similarity handles paraphrase; lexical search handles exact names and phrases; trigram matching handles identifiers and near-miss strings; relationships and temporal constraints provide structural and historical signal.

This matters more for a developer memory system than for a general one. Embeddings smear identifiers, version strings, error codes and stack traces into their semantic neighbourhood — exactly the tokens a debugging agent searches for.

## Decision

Use a hybrid retrieval pipeline combining:

- vector similarity (HNSW, `halfvec` for >= 1024-dim embeddings),
- full-text search (`tsvector` / `ts_rank_cd`, weighted title > digest > content),
- **trigram / identifier search (`pg_trgm`) for exact codes, file paths, symbols and version strings — not optional for this product**,
- graph and relationship signals (bounded traversal from resolved entities),
- temporal constraints (validity filtering plus a recency arm).

Fuse candidate rankings with Reciprocal Rank Fusion at `k = 60`, chosen because it requires no score calibration across arms whose scores live on incompatible scales.

Native full-text ranking is sufficient for the lexical arm at this stage: RRF consumes rank order, and the matching document set is the same regardless of ranking function. Adopt a true BM25 extension only if the evaluation harness demonstrates that lexical ranking is the bottleneck, and note that some BM25 extensions require `shared_preload_libraries`, which constrains managed-Postgres options.

Ranking components and weights are versioned artifacts. Retrieval events record the versions used so that changes can be evaluated and explained.

## Alternatives considered

1. Vector-only retrieval — rejected: exact identifiers, error messages and lexical matches are central to the use case.
2. Keyword-only retrieval — rejected: semantic paraphrase and concept-level retrieval matter.
3. Graph-only retrieval — rejected: most queries are not purely structural.
4. Score-based fusion instead of RRF — rejected initially: it requires calibrating incompatible score scales, which RRF avoids.

## Consequences

Retrieval is more robust and also more complex. Each arm's contribution must be measured; an arm contributing under ~3% of returned items over a month should be removed rather than tuned.

Ranking must be observable and evaluation-gated. A change to weights, prompts, chunking or extraction ships with an evaluation result attached, and only one variable changes at a time.

## Acceptance test

The evaluation harness must be able to compare retrieval configurations and identify whether a ranking change improved or degraded the measured metrics, outside the established noise band.
