# ADR-0012: Controlled Cross-Project Generalisation

## Context

Some knowledge is reusable across projects, but blindly generalising memory creates a serious risk of leaking project-specific or sensitive information. It is simultaneously the highest-leakage feature, the hardest to evaluate, and unnecessary for proving the core product.

## Decision

Build cross-project generalisation last, and ship it disabled by default.

The mechanism is: `generalise -> strip project-specific identifiers, URLs, hostnames and secrets -> propose -> human approve -> shared knowledge`. Raw memories never cross project boundaries; only approved generalisations do.

Memories classified `restricted` are permanently excluded from generalisation, not merely excluded by default.

The first dogfood project is the memory-platform project itself. Additional projects are introduced only after isolation and sensitivity controls are proven in production.

## Alternatives considered

1. Global memory by default — rejected: leakage becomes the default behaviour.
2. Automatic cross-project learning — rejected: extraction cannot reliably judge organizational sensitivity.
3. Never generalise — rejected: carefully approved reusable knowledge is genuinely valuable.

## Consequences

Cross-project learning arrives late and carries additional review requirements.

"The AI learns across all your projects" must not become an early demo feature. It is almost certainly the wrong optimization at this stage, and demonstrating it early creates pressure to enable it before isolation is proven.

The architecture keeps project scope explicit even on generalised records, so provenance survives generalisation.
