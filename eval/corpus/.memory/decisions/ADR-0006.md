# ADR-0006: Bi-Temporal Memory Model

## Context

Memory needs to answer two different questions:

1. When was a fact true? (valid time)
2. When did the system learn or record that fact? (transaction time)

A single timestamp cannot answer both. A migration that happened on 3 August but was recorded on 9 August is not representable with one column, and "what did we believe last month, and when did we find out otherwise?" is one of the few questions this system can answer that a file search cannot.

## Decision

**The model is bi-temporal from day one.** Every memory carries a valid-time interval and a transaction-time record. Supersession is explicit. Historical versions remain queryable. Retrofitting valid time into a live memory store is a rewrite, so "versioning later" is not an option.

**The implementation ambition is deliberately constrained.** Get four invariants right in v1:

1. valid time is recorded and non-overlapping per logical memory key,
2. transaction time is append-only and never mutated,
3. supersession is an explicit edge, not an inferred ordering,
4. historical reconstruction is possible.

Sophisticated temporal querying — interval algebra, complex as-of joins, temporal aggregation — comes later.

### Portability of the mechanism

Prefer PostgreSQL 18 native temporal constraints (`UNIQUE (..., valid_at WITHOUT OVERLAPS)` with `btree_gist`, and `PERIOD` foreign keys). If PG18 is not available in the target distribution, **emulate** with `valid_from`/`valid_until` columns plus exclusion constraints and triggers — but the schema and application semantics assume bi-temporality natively, and migration to the native constraints happens as soon as PG18 is available.

PostgreSQL does not provide system-managed transaction time. That side is implemented with an append-only version table and a trigger.

## Alternatives considered

1. One `created_at` timestamp — rejected: cannot represent delayed discovery or historical truth.
2. Mutable rows without history — rejected: corrections would destroy the evidence of what the system previously believed.
3. Application-only temporal logic — rejected: database-level constraints provide stronger integrity, and the emulation path retains constraint-level enforcement.
4. Full temporal query framework in v1 — rejected: high cost, low early value, and it can be layered on the same data later.

## Consequences

Historical and as-of queries become possible, including the timeline and time-slider features in the console.

The data model and queries are more sophisticated, and temporal constraints need careful testing. Suite 3 of the evaluation harness exists specifically to guard this.
