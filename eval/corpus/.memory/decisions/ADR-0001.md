# ADR-0001: PostgreSQL + pgvector as the Single Memory Store

## Context

The memory platform needs vector retrieval, lexical search, relationships, temporal queries, provenance, ranking signals, and operational data. The tempting design is to introduce separate vector and graph databases early.

That would create multiple sources of truth, additional synchronization paths, more operational infrastructure, and harder disaster recovery before the workload proves that the separation is necessary.

The blueprint treats PostgreSQL as the primary operational store and requires the system to be rebuildable from authoritative git knowledge plus the ingestion event log.

## Decision

Use PostgreSQL 18 with pgvector as the single database store for the MVP and early production system.

Keep embeddings, lexical indexes, graph-shaped entities and relationships, temporal data, retrieval telemetry, and utility signals in PostgreSQL.

Do not introduce a separate vector database or graph database before the system reaches approximately 10 million memories or demonstrates a measured bottleneck that PostgreSQL cannot reasonably address.

Code intelligence remains a separate service/index because code search has materially different indexing and evaluation characteristics.

## Alternatives considered

1. Separate graph database — rejected for the initial architecture because relationships can be represented in PostgreSQL and the operational cost is not justified before demonstrated scale.
2. Separate vector database — rejected because pgvector provides the required vector capability without creating another consistency and recovery boundary.
3. Multiple specialized stores from day one — rejected because premature specialization increases system complexity before workload evidence exists.

## Consequences

Positive:
- One primary operational datastore.
- Simpler transactions and provenance.
- Easier local development and self-hosting.
- Fewer synchronization and failure modes.
- A clear rebuild and disaster-recovery story.

Negative:
- PostgreSQL carries several workloads that may eventually deserve specialization.
- Very large graph or vector workloads may require future architectural changes.
- The architecture must monitor database performance rather than assuming PostgreSQL will scale indefinitely.

### Operational requirement (correctness, not tuning)

Scope predicates are high-selectivity filters applied against an approximate index. With pgvector's defaults, filtering happens after the index scan, so a selective `WHERE` can silently return far fewer rows than requested — or none — with no error.

Therefore:

- Vector queries combined with scope predicates **must** run with `hnsw.iterative_scan = 'relaxed_order'` and a bounded `hnsw.max_scan_tuples`. Unfiltered top-K is not sufficient.
- Composite B-tree indexes with `tenant_id` as the leading column are required so RLS predicates stay index-backed, before any partial per-project HNSW index is considered.
- Recall must be measured **with the scope predicate applied**. Unfiltered recall numbers are not evidence about production behaviour.
- Pin the pgvector minor version in the image tag. Behaviour here changed materially across recent releases.

## Revisit criteria

Reconsider this ADR only when measured workload evidence shows that PostgreSQL is the bottleneck or when memory volume approaches the stated threshold. Any replacement must demonstrate a material improvement and preserve provenance, scope isolation, and rebuildability.

## Acceptance test

The system must be able to answer, from its own stored decision history, why a separate graph database was rejected.
