# ADR-0007: RLS with FORCE, SET LOCAL Scope Context, and Leak Tests

## Context

The platform is multi-tenant and multi-project. A filtering mistake in application code must not expose another project's memories.

Application-level `WHERE project_id = ...` checks alone are too fragile for a trust boundary. Behind a connection pooler, all application connections share one database role, so role-based isolation is also unavailable.

## Decision

Use PostgreSQL Row-Level Security as a mandatory database-level isolation layer, with the mechanisms named explicitly because the near-miss variants fail silently:

- Tables participating in scoped memory access use **`FORCE ROW LEVEL SECURITY`**, not merely `ENABLE`. Without `FORCE`, the table owner bypasses every policy with nothing erroring and everything appearing filtered.
- Scope context is established with **`SET LOCAL`** (or `set_config(..., true)`) inside each transaction, **never bare `SET`**. Under transaction-mode pooling, a session-scoped setting persists on the connection and the next client inherits the previous tenant's context. A single `false` third argument is a latent breach.
- The application role is **not** the table owner and is created `NOBYPASSRLS`.
- Clients must not be able to set `app.*` settings themselves; only the trusted server path may call the scope-setting function.
- Scope predicates are additionally pushed into every candidate-generation query, both for defence in depth and because post-hoc filtering of approximate index results is incorrect (ADR-0001).
- Composite indexes lead with `tenant_id` so policy predicates stay index-backed. Measured overhead with correct indexing is a few percent.

Every new scoped table ships with negative pgTAP tests proving that an actor cannot read or mutate data outside its authorized ScopeSet. **RLS tests are a merge gate**, implemented twice — at the database layer with pgTAP and at the API layer through the real gateway.

## Alternatives considered

1. Application-only filtering — rejected: a missed filter is a data leak with no error.
2. Database-per-project — rejected for the MVP: operational cost and poor fit for a shared platform with org-wide knowledge.
3. Role-based RLS (`current_user`) — rejected: worthless behind a pooler where every connection shares a role.
4. Trusting client-supplied scope — rejected: clients are not authorization authorities.

## Consequences

Cross-project isolation is enforced close to the data, and survives application bugs.

Development and testing become more demanding: every query path must correctly establish scope context, and the connection wrapper should make it impossible to open a transaction without one.

Policy regressions are silent — no error, just wrong rows returned — so automated cross-tenant tests are the only reliable guard. They are treated exactly like auth tests.

## Kill criterion

Any confirmed cross-project leak freezes feature development until the isolation model is audited and independently reviewed.
