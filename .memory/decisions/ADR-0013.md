# ADR-0013: Provider Abstraction

## Context

Embedding models, LLM providers and rerankers will change. Hard-coding a provider into the storage and retrieval model would make migrations expensive and undermine the stated provider-independence goal.

At the same time, abstraction must not become a layer that prevents useful model migrations or experiments.

## Decision

Introduce provider abstraction boundaries for embeddings, LLM extraction and generation, and reranking.

Support **two embedding models active simultaneously** so migration and side-by-side evaluation can happen without an all-at-once cutover. Embeddings are stored in their own table keyed by model identity, with dimensions and normalization recorded.

Provider and model identifiers are versioned and recorded on the artifacts and retrieval events that depend on them, so a quality change can be attributed to a model change.

Default to local models for the local-first deployment; remote providers are configuration, not architecture.

## Alternatives considered

1. Hard-code one provider — rejected: unnecessary lock-in and a stated constraint violation.
2. Abstract every component immediately — rejected: excessive abstraction slows the MVP.
3. A single active embedding model — rejected: safe migration and comparative evaluation require coexistence.

## Consequences

Provider migration and evaluation become routine rather than a project.

More metadata and interface discipline are required, and provider-specific behaviour must be tested behind the abstraction rather than assumed equivalent.
