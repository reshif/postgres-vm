# ADR-0017: The Headline Gate Is Out of Scope

## Context

04-EVALUATION.md §7.2 defines the gate the project turns on: arm D (full memory
loop) must beat arm B (filesystem + grep + `AGENTS.md`) on at least three of five
metrics, measured over the full task set, mean ± σ across five runs, outside the
noise band. ADR-0014 keeps that as a permanent kill criterion rather than a
one-time comparison, and §7.2 states the consequence of failing it plainly: stop,
and ship the two-plane git convention alone.

The measurement has never been run. `eval/agent_benchmark.json` authors 20 tasks,
five arms and `repetitions: 5`; what does not exist is a runner that drives an
agent through them. Producing the number means roughly 500 agent sessions across
both arms, with the token cost that implies.

The platform is operated by one person, on one repository, for their own use. The
claim §7.2 exists to test — that this packaging beats grep for a team — is not a
claim being made.

## Decision

**Do not run the §7.2 headline gate, and do not make the claim it would license.**

The platform is scoped explicitly as a single-operator tool. It is not asserted
to outperform a filesystem-and-grep baseline, because that number does not exist
and will not be produced under this scope.

This is a decision not to ASK the question, which is different from failing it.
Nothing here reinterprets a measurement, and no threshold is lowered.

**§7.3 is not waived.** The production gate is about operational safety —
isolation, injection, latency, recoverability — and every item on it continues to
be measured and reported. `eval/go_no_go.py` reports §7.2 as out of scope by this
ADR and keeps reporting §7.3 truthfully, including the items currently failing.

**Known consequence, accepted:** capabilities C1 (rationale recovery), C2
(recurrence) and C6 (procedure execution) stay unmeasured, because each needs the
same agent-in-the-loop harness. They are recorded as NOT MEASURED, never as
passing.

## Revisit condition

This ADR is scoped to single-operator use, and that scope is the whole
justification. **If the platform is offered to anyone else — another person, a
team, or as a product — §7.2 must be run before the claim is made.** Crossing
that line without the measurement would be shipping on partial credit, which
§7.2 names as the outcome to avoid.

## Alternatives considered

1. **Run it with an LLM driver.** Rejected for now on cost and because the claim
   it establishes is not being made. This remains the correct action the moment
   the revisit condition is met.
2. **Build the runner and leave it unrun.** Rejected as the worst of both: the
   maintenance cost of a harness with none of the information, and a standing
   temptation to quote a partial run.
3. **Soften the gate to something achievable.** Rejected. §7.2 requires any
   softening to be its own ADR with reasoning recorded; that is what this
   document is, and it scopes the gate OUT rather than moving the bar, because
   moving the bar would leave a number that looks like a passed gate and is not.

## Related: the p95 latency gate

Separately and deliberately NOT softened: §7.3's "p95 `memory.context` < 350 ms"
currently fails at roughly 10 s, because the cross-encoder reranker runs on an
integrated GPU. The operator has chosen retrieval quality over latency while
testing alone, and to revisit on better hardware. That gate therefore continues
to be reported as FAILING rather than adjusted to fit the hardware. An accepted
failure that is still measured stays visible; a gate rewritten to pass does not.
