# ADR-0003: Four-Tool MCP Surface with Resources

## Context

The earlier design exposed many specialized MCP tools. That makes the protocol surface harder to learn, harder to secure, and easier to expand into an accidental agent framework.

The memory platform's core responsibility is context retrieval and memory lifecycle, not exposing every internal operation as an agent-facing tool. Tool-count bloat also has a measurable cost: irrelevant tool options consume the attention budget that should go to task reasoning.

## Decision

Keep the MCP interface deliberately small: four primary tools plus resources.

- `memory.context` — intent in, minimal sufficient context pack out.
- `memory.search` — specific questions, and expansion of refs.
- `memory.write` — record something durable.
- `memory.explain` — provenance, versions, and retrieval score decomposition.

Resource URIs cover the rest: project profile and state, timelines, procedures index, single memories, entities, conflicts.

The governing invariant:

> **MCP exposes intent, not implementation.**

The internal context engine may contain many components — planner, fusion, reranker, deduplicator, conflict resolver, budget allocator — but none of them is automatically promoted to a separate MCP tool. `reflect`, `timeline`, `related`, `procedures` and `consolidate` are scheduler or console concerns, or parameters on the four tools.

The four-tool constraint is preserved unless evaluation proves otherwise. The specific four may evolve; the constraint should not.

## Alternatives considered

1. Eleven or more specialized MCP tools — rejected because the surface becomes an implementation API rather than a stable context-engine contract, and because it forces the agent to choose a retrieval strategy.
2. One opaque tool — rejected because the agent-facing contract would become less discoverable and less semantically clear.
3. A full orchestration interface — rejected because the product is memory and context infrastructure, not an agent framework.

## Consequences

The MCP contract stays small and stable. Internal architecture can evolve without multiplying externally visible tools. Some operations must be composed internally or exposed as resources rather than new tools.

Tool listings are returned in deterministic order with cache hints, so clients and prompt caches can hold them.

## Acceptance test

A normal agent workflow must be able to perform context retrieval, search, memory writes, and explanation without requiring a proliferation of specialized MCP tools.
