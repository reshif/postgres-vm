# ADR-0010: PostgreSQL-Backed Background Jobs

## Context

The platform needs asynchronous work for ingestion, embedding, extraction, consolidation, decay and indexing.

Introducing Redis solely as a queue would add another infrastructure dependency to a system intentionally designed around PostgreSQL and a local-first deployment constraint.

## Decision

Use a PostgreSQL-backed job queue, initially Procrastinate, which uses `LISTEN`/`NOTIFY` and `FOR UPDATE SKIP LOCKED`.

Queue state lives alongside the transactional data that schedules the work, so a memory write and its associated background job are coordinated in one transaction. That removes an entire class of orphaned-job bugs.

Do not add Redis to the MVP.

## Alternatives considered

1. Redis/Celery — rejected for the initial system: another operational dependency, and Celery does not use PostgreSQL as a broker.
2. In-process background tasks — rejected: not durable enough for production workflows.
3. A separate queue service — deferred until measured throughput justifies it.

## Consequences

Fewer infrastructure components and simpler local deployment.

PostgreSQL now carries queue workload alongside memory workload, so queue throughput and table bloat must be monitored, with aggressive autovacuum settings on the job tables.

## Revisit criteria

Reconsider only if the PostgreSQL-backed queue becomes a demonstrated bottleneck, and record the measurement in the superseding ADR.
