# ADR-0004: Stateless MCP Protocol and Server-Resolved Scope

## Context

A memory server must support many agents, projects, and tenants without carrying state from one request or client into another.

Client-supplied project or tenant identifiers are not trustworthy authorization boundaries. A design that relies on MCP environment variables or client-provided IDs can be manipulated or misconfigured.

The current MCP specification revision removes protocol-level sessions and the initialize handshake outright, so this is also a conformance requirement, not only a design preference.

## Decision

**Lock: no protocol-session state.** Memory identity, authorization and project binding never depend on an MCP connection or session.

Every request is independently authenticated and authorized. The server derives the principal and the permitted ScopeSet from trusted token identity (remote transport) or verified process context and git binding (stdio). Client-supplied scope identifiers are request hints at most; they are never the authority for access control. Every downstream call receives the server-resolved ScopeSet.

**Do not lock: "the system is stateless."** That is a different and harmful claim. Application state is permitted where the work genuinely requires it — long-running ingestion, re-embedding, human approval, resumable extraction — provided it is:

- **explicit** — represented as a server-minted handle passed as an ordinary argument, never implied by the connection;
- **durable** — stored in PostgreSQL, not in process memory;
- **attributable** — bound to a principal and a scope, and auditable.

`pack_id` and task handles are exactly this pattern.

```
MCP protocol state    ->  none
Application state     ->  explicit handle -> PostgreSQL -> auditable, resumable, attributable
```

## Alternatives considered

1. Stateful MCP sessions — rejected: complicates horizontal scaling, failure recovery and isolation, and is no longer supported by the specification.
2. Trusting client-provided project IDs — rejected: clients are not authorization authorities.
3. Scope from MCP environment variables — rejected: those values are client-controlled.
4. Blanket statelessness as an architectural invariant — rejected: it would force redesign the first time a legitimately long-running or resumable operation appears, and it confuses transport semantics with system capability.

## Consequences

The gateway scales horizontally and every request carries an explicit, auditable security context.

The server must perform reliable token → principal → ScopeSet resolution and propagate that scope consistently through the entire request path, including into the database session context.

Any new stateful capability must arrive with its handle model, its storage, and its audit story — not as an implicit session.

## Security requirement

Scope isolation is a hard invariant. RLS and application-level scope handling must agree, and cross-project leakage is a release-blocking failure.
