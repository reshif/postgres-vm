# ADR-0002: Two-Plane Memory Architecture

## Context

Not all memory is produced in the same way. Architectural decisions and procedures are deliberately authored and reviewed, while episodes, observations, candidates, embeddings, relationships, and retrieval telemetry are produced continuously by the system.

Putting everything into database rows creates a trust and review problem: humans cannot meaningfully diff or code-review an automatically generated database state.

## Decision

Split memory into two planes.

**Plane A — the authoritative knowledge ledger**
- Lives in the project repository under `.memory/`.
- Is versioned by git.
- Contains decisions, procedures, conventions, constraints, preferences, glossary and project metadata.
- Changes enter through human-authored commits or agent-proposed diffs reviewed through the normal code-review process.

**Plane B — the operational projection and evidence layer**
- Lives in PostgreSQL.
- Contains episodes, observations, candidates, entities, relationships, embeddings, retrieval telemetry, utility scores, and the materialized index of Plane A.
- Is written by system processes.

Plane A is not "memory storage" and Plane B is not "a second source of truth." The distinction is one of authority and lifecycle, and it must be visible in the schema, the ingestion pipeline, the API semantics, the evaluation harness, and the recovery procedure.

### Invariants

1. **Plane B never promotes itself.** The only path from Plane B to authoritative knowledge is: proposal → human review → git commit → ingestion. There is no direct database write to authoritative status.
2. **One context engine, two planes.** Plane A is indexed into Plane B's retrieval machinery. There are not two retrieval stacks.
3. **Plane B must be rebuildable** from Plane A plus the append-only ingestion event log. This is a hard invariant, verified quarterly.
4. **Sync is one-way by default.** `.memory/` is read by a git connector like any other ingestion source, at the highest trust tier.
5. **Two review paths, no mixing.** Plane A changes are reviewed in git. Plane B candidates are reviewed in the console inbox.
6. **Degraded mode is acceptable.** If git is unreachable, the database serves the last-known state of Plane A; Plane A updates queue. Plane A changes slowly, so this is tolerable.

## Alternatives considered

1. Single database plane — rejected because authoritative knowledge would lose ordinary diff, blame and review semantics, and because a failed evaluation would leave nothing shippable.
2. Git-only memory — rejected because episodes, temporal retrieval, embeddings, ranking, and observations are not practical as reviewed files.
3. Two independent authoritative stores — rejected because it creates ambiguity about which source is canonical.
4. Independent retrieval stacks per plane — rejected as unnecessary complexity.

## Consequences

The architecture gains trust, reviewability, portability, graceful degradation, and a clean separation between authored knowledge and continuously generated observation.

It also introduces ingestion and synchronization machinery, a git connector, and lag between commit and retrievability (SLO: < 60s via webhook). That complexity is accepted because the two planes represent two genuinely different production processes.

### Human dependency

This model has a named human dependency and it belongs in the ADR rather than in a footnote. The review inbox requires a curator spending roughly 30 minutes per week (see ADR-0015). If no curator is available, the system **must** degrade to deterministic-only extraction with no LLM quarantine pipeline. Auto-extraction without review is a security failure mode, not a convenience.

## Acceptance test

Delete the database, re-index Plane A from git, replay the ingestion event log, and verify that the resulting system remains operational and scores within the defined evaluation tolerance (>= 95% of the previous run).

If the rebuild drill or the git connector proves infeasible during implementation, the response is to fix the connector or the drill — not to collapse to a single plane.
