# ADR-0014: Evaluation Before Optimization

## Context

A memory system can become more sophisticated without becoming more useful. Semantic retrieval, graph signals, reranking, learned utility and extraction each create opportunities for silent regression.

The simplest honest competitor is not "no memory." It is the repository's authoritative `.memory/` files plus filesystem and grep retrieval, with a good `AGENTS.md`. That competitor has real evidence behind it: a plain agent given transcripts as files scored competitively against dedicated memory systems, and at least one major coding agent ships grep-only retrieval after finding it worked better.

Published agent-memory benchmark numbers are not usable as targets: vendors run their own answer models, judge models and question subsets, and a model swap alone can move scores by around ten points.

## Decision

Build an evaluation harness with, at minimum, these arms, run on our own repositories:

- **A** cold agent, no memory, no `AGENTS.md`
- **B** filesystem + grep + `AGENTS.md` (the honest baseline)
- **C** memory, retrieval only
- **D** memory, full loop
- **E** full context (ceiling and cost reference)

**The baseline is a permanent control arm, not a one-time comparison.** It runs on every end-to-end evaluation, forever. The headline claim is always D against B; D against A is marketing.

### Capability-scoped advantage

The system is not trying to beat grep at grep's job, and a requirement to do so would be dishonest in both directions. The standard is:

> A capability ships when it demonstrates measurable advantage over the strongest honest baseline **for the tasks that capability claims to solve**, and is not materially worse on the tasks the baseline already handles well.

The capabilities this system claims, and which the harness must measure separately:

- why a decision was made, and what it superseded
- whether a failure has been seen before, and how it was solved
- what was believed at time T, and when that changed
- which knowledge is authoritative versus unreviewed
- which knowledge applies to this project and must not apply to another
- which procedure solved a class of problem

Measure per capability and per arm: retrieval recall, answer accuracy, provenance correctness, temporal correctness, leakage, repeated-question rate, repeated-failed-approach rate, time to diagnosis, token cost, latency, and human preference.

### Kill criterion (retained deliberately)

Capability-scoped measurement must not become an escape from a stop condition. At the Phase 6 gate, arm D must beat arm B on at least **3 of 5** headline metrics:

1. repeated questions reduced >= 40%
2. turns to completion reduced >= 15%
3. task success improved >= 10 percentage points
4. total tokens not worse by more than 10%
5. repeated failed approaches reduced >= 50%

If it does not, stop expanding the memory system and ship the two-plane git convention alone. That is a real product and a legitimate outcome, and discovering it in month four is a success.

Any future softening of this gate is itself an ADR, with the reasoning recorded.

## Alternatives considered

1. Evaluate only the memory-enabled system — rejected: no evidence the machinery beats a simple solution.
2. Optimize by intuition — rejected: regressions stay invisible.
3. Require the system to beat grep universally — rejected: the wrong test; grep is excellent at its job and the product does not claim to replace it.
4. Capability-scoped claims with no stop condition — rejected: that is how projects run indefinitely on the promise of the next feature.
5. Build evaluation at the end — rejected: the baseline must exist before optimization begins.

## Consequences

Evaluation is normal engineering, not a final demonstration. Some apparently sophisticated features will be shipped disabled because they do not beat the baseline for their claimed capability.

The golden set is owned by a named person, versioned in git, rebuilt from production traces quarterly, and every incident becomes a case within a week.

Retrieval events record the artifact versions used, so a quality change is attributable.

## Acceptance test

The platform must be able to demonstrate quantitatively, per claimed capability, whether memory improves agent outcomes over the filesystem + grep baseline — and must be able to show the same numbers for the arm where it does not.
